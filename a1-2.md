Here are test ideas for the secure document upload feature, grouped by quality characteristic. Each idea targets a specific risk. Because these are legal documents, the cost of a failure is high: a corrupted contract, a leaked privileged document or a missing audit entry can all have legal consequences.

## Functionality

**Risk: the system accepts files it shouldn't, or rejects files it should accept.**

1. Upload a valid PDF, DOCX and TXT file. Each is accepted, stored and listed for the uploader.
2. Upload formats that paralegals commonly have but are **not** in the supported list: DOC, RTF, ODT, XLSX, scanned images (JPG/PNG/TIFF), ZIP, and email files (MSG/EML). Each is rejected with a message that names the supported formats.
3. Upload files with uppercase or mixed-case extensions (`CONTRACT.PDF`, `Brief.Docx`). They are accepted.
4. Upload a file whose extension doesn't match its content: a JPG renamed to `.pdf`, an executable renamed to `.docx`. The file is rejected based on its content, not its extension.
5. Upload a file with no extension, or a double extension (`contract.pdf.exe`). It is rejected.
6. Upload variants of the supported formats: PDF/A, password-protected PDF, PDF with fillable forms or annotations, a macro-enabled `.docm` renamed to `.docx`, a DOCX with tracked changes and comments, and TXT files in UTF-8, UTF-16 and UTF-8 with a BOM. Confirm which variants should be accepted, and that accepted ones open correctly afterwards.

**Risk: the 20MB limit is enforced inconsistently or can be bypassed.**

7. Boundary values: 0 bytes, 1 byte, just under 20MB, exactly 20MB, 20MB + 1 byte, and a much larger file (e.g., 500MB). Only files up to 20MB are accepted.
8. Check whether "20MB" means 20,000,000 bytes or 20,971,520 bytes (20 MiB), and that the client and the server use the same value. Upload a file between the two sizes to expose any mismatch.
9. Bypass the client-side size check by sending the request directly to the upload API. The server still rejects files over 20MB.
10. Upload a file far over the limit. It is rejected early, not after the whole file has been transferred.

**Risk: progress updates are missing, misleading or wrong.**

11. The progress indicator appears as soon as the upload starts and reaches 100% when it finishes.
12. Upload a very small TXT file (fast) and a 20MB PDF over a throttled connection. Both show meaningful progress, not a bar that jumps straight to 100% or freezes.
13. Progress does not show 100% or "success" before the server has confirmed the document is stored.
14. Progress reflects failures: network drop mid-upload, server error, or rejection after transfer (e.g., by a virus scan). The user sees an error, not a stuck or completed bar.
15. Upload several documents in parallel (if supported). Each has its own accurate progress indicator.
16. Navigate away or close the tab mid-upload. Is the user warned? What happens to the partial document?

**Risk: everyday upload scenarios behave unexpectedly.**

17. Upload a document with the same name as one already uploaded. There is no silent overwrite: both versions are kept, or the user is asked.
18. Use file names with spaces, Unicode (Thai, accented characters), very long names, and special characters (`& # % ' "`). They are stored and displayed correctly.
19. Cancel an upload partway. No partial document appears in the user's list.
20. Retry after a failed upload. It succeeds without creating duplicates.

## Data Integrity

**Risk: the stored document differs from the original.**

21. Download each uploaded document and compare its checksum (e.g., SHA-256) with the original, for each format and for a file of exactly 20MB. The files are byte-for-byte identical.
22. Interrupt uploads at different points (e.g., 50% and 99%). No truncated or corrupt document is stored or shown as complete.
23. File metadata is stored correctly: original file name, type, size, upload time and uploader.
24. Internal document metadata (author, tracked changes, comments, embedded files) is not stripped or altered. For legal documents this information may itself be evidence.
25. TXT encodings and line endings (CRLF vs LF) are not converted during upload or download.

**Risk: documents get mixed up between users or uploads.**

26. Two users upload files with the same name at the same time. Each document is linked to the right owner, and neither overwrites the other.
27. The same user uploads the same file twice. The behavior is defined and consistent (a duplicate is stored, or the duplicate is detected).

**Risk: the audit report is incomplete or inaccurate.**

28. The audit record for a successful upload matches what actually happened: correct user, file name, size, date and time (check the time zone), and result.
29. An audit record is created for **failed** uploads too (unsupported format, too large, network failure, cancelled, virus detected), with the reason for the failure.
30. The audit record never says "successful" when the document failed to store (e.g., a storage error after the transfer finished), and never says "failed" for a document that was stored.
31. Make the auditing feature unavailable during an upload. Is the upload blocked, queued, or allowed without an audit record? No upload should go unaudited.
32. The paralegal (and other ordinary users) cannot edit or delete audit records.

## Security

**Risk: someone other than the uploader can access the document.**

33. After upload, try to view, download or list the document as another paralegal, a user from another team or client matter, and an administrator. All are denied. (Confirm with the team whether administrators should also be denied.)
34. Request the document directly by its URL or ID while logged out, or as another user. Access is denied by the server (403/404), not just hidden in the UI.
35. Guess or enumerate document IDs (e.g., sequential IDs). No access to other users' documents, and no information leaks such as file names or whether a document exists.
36. Search results, previews, thumbnails and "recent files" lists don't expose the document to other users.
37. If download links are generated (e.g., pre-signed URLs), check that they expire and can't be used by someone else.
38. The document stays private until the uploader explicitly shares it. Nothing is shared by default, for example through a team folder or default sharing settings.

**Risk: a malicious file harms the system or other users.**

39. Upload the EICAR antivirus test file inside a PDF, a DOCX and a TXT. It is detected and rejected or quarantined.
40. Upload a PDF with embedded JavaScript, launch actions or embedded files, and a DOCX with macros, external template links or OLE objects. They are handled safely and nothing is executed by the server or any previewer.
41. Upload malformed or crafted files: a corrupt PDF, a DOCX "zip bomb", and a DOCX containing an XML External Entity (XXE) payload. The server doesn't crash, hang or leak data.
42. Use malicious file names: `../../etc/passwd.pdf`, `<script>alert(1)</script>.pdf`, a null byte (`file.pdf%00.exe`), and SQL injection strings. Names are sanitized when stored and escaped when displayed, including in the audit report.
43. Spoof the `Content-Type` header. The server validates the actual file content, not the header.

**Risk: documents are exposed in transit or at rest, or the upload can be abused.**

44. Uploads only work over HTTPS. HTTP requests are redirected or refused.
45. Stored documents are encrypted at rest, and the storage location (e.g., a cloud bucket) is not publicly accessible.
46. The upload endpoint requires a valid, authenticated session. If the session expires mid-upload, the upload fails safely.
47. Cross-site request forgery (CSRF): a malicious website can't trigger an upload on behalf of a logged-in paralegal.
48. Many large uploads in a short time don't exhaust storage or make the service unavailable (rate limiting / quotas).
49. Error messages don't reveal internal details such as stack traces, storage paths or server versions.
50. The audit log doesn't store document content, and is itself protected so only authorized roles can read it.

## Questions to clarify with the team

Some acceptance criteria are open to interpretation. Clarifying them will sharpen the tests above:

- Is 20MB measured as 20,000,000 bytes or 20,971,520 bytes?
- Should administrators or support staff be able to access uploaded documents?
- Are password-protected PDFs and documents containing macros allowed?
- What exactly goes into the audit record (fields, failure reasons), who can read it, and how long is it kept?
- What does "progress update" mean in practice: a percentage, a progress bar, or status messages?
- Should duplicate uploads be detected?
